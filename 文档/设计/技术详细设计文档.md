## 一、背景与目标

### 1.1 需求来源

本系统基于技术面试场景需求设计，旨在展示系统设计能力和编码水平。需求来源于真实电商业务场景，参考京东商城等实际系统的核心交易流程。

**原始需求**：
- 实现用户与商家之间的商品交易流程
- 支持用户预存账户充值
- 支持商家库存管理
- 实现下单购买的原子操作（扣款、减库存、加余额）
- 提供每日结算对账功能

### 1.2 业务背景

随着电商行业的快速发展，构建一个稳定、可靠的商品交易系统成为核心需求。本系统需要解决以下业务问题：

1. **资金安全**：确保用户充值、扣款、商家收款的准确性
2. **库存一致性**：防止超卖，保证库存数据的准确性
3. **账务对账**：提供清晰的账务对账机制，确保财务数据准确
4. **高并发处理**：支持多用户同时下单，保证系统稳定性

### 1.3 设计目标

#### 业务目标
- ✅ 实现完整的商品交易闭环：充值 → 上架 → 下单 → 支付 → 结算
- ✅ 保证交易的准确性和一致性，避免超卖、重复扣款等问题
- ✅ 提供清晰的账务对账机制，确保财务数据准确

#### 技术目标
- ✅ 采用DDD领域驱动设计，合理划分业务边界
- ✅ 实现高内聚低耦合的模块化设计
- ✅ 核心代码单元测试覆盖率达到80%以上
- ✅ 具备良好的可扩展性，支持后续功能迭代
- ✅ 支持500 TPS并发订单处理能力
- ✅ 阶段1响应时间 < 50ms（P95）
- ✅ 完整流程处理时间 < 2s（P95）

### 1.4 本次设计要解决的问题

1. **如何保证高并发下的数据一致性**：通过乐观锁 + 事件驱动架构解决
2. **如何缩短事务持有锁时间**：通过四阶段事件驱动拆分长事务
3. **如何防止超卖**：通过乐观锁版本控制 + SELECT FOR UPDATE
4. **如何保证幂等性**：通过requestId唯一索引 + 事件ID去重
5. **如何处理失败补偿**：通过OrderFailedEvent触发退款和库存恢复
6. **如何限流保护系统**：通过拦截器 + Guava RateLimiter实现分层限流

## 二、需求说明

### 2.1 功能需求

#### 2.1.1 用户模块

**F1. 账户充值**
- 用户可以通过REST API向预存账户充值
- 充值金额范围：0.01 ~ 10,000元（可配置）
- 必须支持幂等性（requestId去重）
- 充值成功后立即更新余额

**F2. 余额查询**
- 查询用户当前余额
- 返回货币类型（CNY）

**F3. 充值记录查询**
- 分页查询用户的充值记录
- 支持按时间范围筛选

---

#### 2.1.2 商家模块

**F4. 添加/更新库存**
- 商家可以通过REST API向库存中添加商品
- SKU格式规范：`^[A-Z0-9_]+$`
- 如果SKU已存在，累加库存数量
- 允许更新已存在商品的价格

**F5. 查询商品信息**
- 查询指定SKU的商品信息（价格、库存、已售）

**F6. 商家账户查询**
- 查询商家当前余额和累计收入

**F7. 结算对账**
- 每天凌晨02:00自动执行对账任务
- 对比昨日销售总额和收款总额
- 不一致时记录告警

**F8. 对账记录查询**
- 查询指定日期范围的对账记录

---

#### 2.1.3 交易模块

**F9. 创建订单**
- 用户提供SKU和购买数量
- 系统完成扣款、减库存、加商家余额
- 返回订单ID和状态

**F10. 订单详情查询**
- 查询指定订单的详细信息（含订单项）

**F11. 用户订单列表查询**
- 分页查询用户的订单列表
- 支持按状态筛选

### 3.4 核心设计思路

#### 3.4.1 DDD领域驱动设计

**限界上下文划分**：
- User Context：用户账户管理
- Merchant Context：商家库存管理
- Trade Context：订单交易管理

**聚合根设计原则**：
- 每个聚合根保证内部数据一致性
- 通过聚合根访问实体
- 聚合间通过领域事件通信

---

#### 3.4.2 事件驱动架构

**设计理念**：
- 将长事务拆分为4个短事务
- 通过事件串联，保证最终一致性
- 缩短事务持有锁时间，提升并发性能

**事件链**：
```
OrderCreatedEvent → UserBalanceDeductedEvent → InventoryDeductedEvent → OrderCompletedEvent
```

---

#### 3.4.3 分层限流策略

**三层架构**：
1. 全局限流：1000 TPS（可选）
2. 接口级限流：订单创建600 TPS、充值200 TPS
3. 用户级限流：单用户下单10 TPS、充值5 TPS

**实现方式**：
- 自定义注解 @RateLimit
- HandlerInterceptor拦截器
- Guava RateLimiter令牌桶算法

## 四、详细设计

### 4.1 业务流程设计

#### 4.1.1 用户充值流程

**流程图**：
```
开始
  ↓
接收充值请求(userId, amount, requestId)
  ↓
验证参数(amount > 0, amount <= 10000)
  ├─ 失败 → 返回400错误
  ↓
检查幂等性(requestId唯一索引)
  ├─ 已存在 → 返回上次结果
  ↓
开启事务
  ↓
查询用户账户(SELECT FOR UPDATE)
  ├─ 不存在 → 创建新账户
  ↓
更新余额(balance = balance + amount)
  ↓
记录充值流水
  ↓
提交事务
  ↓
返回充值结果和最新余额
  ↓
结束
```

**异常流程**：
- 充值金额为0或负数 → 返回400错误："充值金额必须大于0"
- 充值金额超过上限 → 返回400错误："充值金额超出限制"
- 数据库异常 → 事务回滚，返回500错误

**关键代码位置**：
- Controller: `UserController.recharge()`
- Service: `UserService.recharge()`
- Mapper: `UserAccountMapper.selectForUpdate()`, `UserAccountMapper.updateBalance()`

---

#### 4.1.2 商家添加库存流程

**流程图**：
```
开始
  ↓
接收添加库存请求(merchantId, sku, quantity, price)
  ↓
验证参数(sku格式, price > 0, quantity > 0)
  ├─ 失败 → 返回400错误
  ↓
开启事务
  ↓
查询库存记录(SELECT FOR UPDATE)
  ↓
判断是否存在
  ├─ 存在 → 累加库存数量，可选更新价格
  └─ 不存在 → 创建新库存记录
  ↓
提交事务
  ↓
返回最新库存信息
  ↓
结束
```

**异常流程**：
- SKU格式错误 → 返回400错误："SKU格式不正确"
- 价格或数量不合法 → 返回400错误
- 并发添加 → 行锁等待，超时后重试

**关键代码位置**：
- Controller: `MerchantController.addStock()`
- Service: `MerchantService.addStock()`
- Mapper: `ProductInventoryMapper.selectBySkuForUpdate()`, `ProductInventoryMapper.upsert()`

#### 4.1.3 用户下单购买流程（核心）

**四阶段时序图**：
```
用户          Trade Context       User Context      Merchant Context
 │                  │                  │                  │
 │──创建订单──────▶│                  │                  │
 │                  │──验证库存余额──│                  │
 │                  │──创建订单──────│                  │
 │                  │──发布事件─────│                  │
 │◀──返回订单ID───│                  │                  │
 │                  │                  │                  │
 │                  │──异步触发─────▶│                  │
 │                  │                  │──扣减余额──────│
 │                  │                  │──发布事件─────│
 │                  │                  │                  │
 │                  │                  │──异步触发─────▶│
 │                  │                  │                  │──扣减库存
 │                  │                  │                  │──增加余额
 │                  │                  │                  │──发布事件
 │                  │                  │                  │
 │                  │◀──异步触发──────│                  │
 │                  │──更新订单状态──│                  │
 │                  │                  │                  │
```

**阶段1：订单创建（同步事务）**
```
1. 限流检查（接口级 + 用户级）
2. 验证用户身份
3. 查询商品信息（价格、库存）
4. 验证库存充足性
5. 计算订单总金额（quantity × price）
6. 验证用户余额充足性
7. 创建订单记录（状态=CREATED）
8. 创建订单项
9. 发布OrderCreatedEvent
10. 提交事务
11. 返回订单ID
```

**阶段2：资金扣减（异步事件处理）**
```
1. 监听OrderCreatedEvent
2. 开启新事务
3. 查询用户账户
4. 扣减用户余额（乐观锁）
5. 记录扣款流水
6. 发布UserBalanceDeductedEvent
7. 提交事务
```

**阶段3：库存扣减与收款（异步事件处理）**
```
1. 监听UserBalanceDeductedEvent
2. 开启新事务
3. 查询库存记录
4. 扣减库存（乐观锁）
5. 增加商家余额（乐观锁）
6. 记录收款流水
7. 发布InventoryDeductedEvent
8. 提交事务
```

**阶段4：订单完成（异步事件处理）**
```
1. 监听InventoryDeductedEvent
2. 开启新事务
3. 查询订单
4. 更新订单状态为COMPLETED
5. 发布OrderCompletedEvent
6. 提交事务
```

**异常补偿流程**：
```
任一阶段失败
  ↓
发布OrderFailedEvent（携带failedStage）
  ↓
User Context监听
  ├─ failedStage = BALANCE_DEDUCTION → 无需补偿
  └─ failedStage = INVENTORY_DEDUCTION → 执行退款
  ↓
Merchant Context监听
  ├─ failedStage = BALANCE_DEDUCTION → 无需补偿
  └─ failedStage = INVENTORY_DEDUCTION → 恢复库存
  ↓
Trade Context监听
  ↓
更新订单状态为FAILED
  ↓
记录异常日志
```

**关键代码位置**：
- 阶段1: `OrderService.createOrder()`
- 阶段2: `UserBalanceEventListener.handleOrderCreated()`
- 阶段3: `InventoryEventListener.handleUserBalanceDeducted()`
- 阶段4: `OrderStatusEventListener.handleInventoryDeducted()`
- 补偿: `UserBalanceEventListener.handleOrderFailed()`, `InventoryEventListener.handleOrderFailedForStockRestore()`

#### 4.1.4 商家每日结算对账流程

**流程图**：
```
定时任务触发（每天02:00）
  ↓
遍历所有商家
  ↓
对每个商家执行：
  ├─ 统计昨日销售总额
  │   SELECT SUM(quantity * unit_price) 
  │   FROM order_item JOIN orders
  │   WHERE merchant_id = ? AND status = 'COMPLETED'
  │   AND DATE(create_time) = ?
  ├─ 查询昨日收款总额
  │   SELECT SUM(amount) 
  │   FROM merchant_credit_record
  │   WHERE merchant_id = ? AND DATE(created_at) = ?
  ├─ 对比两个金额
  │   ├─ 一致 → 对账状态 = MATCHED
  │   └─ 不一致 → 对账状态 = MISMATCHED
  ├─ 生成对账记录
  └─ 不一致 → 记录告警日志
  ↓
记录任务执行日志
  ↓
结束
```

**关键代码位置**：
- Job: `SettlementJob.execute()`
- Service: `SettlementService.settle()`
- Mapper: `SettlementRecordMapper.insert()`

### 4.2 数据设计

#### 4.2.1 表结构设计

**user_account（用户账户表）**
```sql
CREATE TABLE user_account (
    user_id BIGINT PRIMARY KEY COMMENT '用户ID',
    balance DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '余额',
    currency VARCHAR(3) NOT NULL DEFAULT 'CNY' COMMENT '货币类型',
    version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    INDEX idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户账户表';
```

**recharge_record（充值记录表）**
```sql
CREATE TABLE recharge_record (
    recharge_id VARCHAR(32) PRIMARY KEY COMMENT '充值ID',
    user_id BIGINT NOT NULL COMMENT '用户ID',
    amount DECIMAL(10,2) NOT NULL COMMENT '充值金额',
    request_id VARCHAR(64) NOT NULL UNIQUE COMMENT '请求ID（幂等性）',
    status VARCHAR(20) NOT NULL DEFAULT 'SUCCESS' COMMENT '充值状态',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    INDEX idx_user_id (user_id),
    INDEX idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='充值记录表';
```

---

**product_inventory（商品库存表）**
```sql
CREATE TABLE product_inventory (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键',
    sku VARCHAR(64) NOT NULL COMMENT 'SKU',
    merchant_id BIGINT NOT NULL COMMENT '商家ID',
```

### 4.4 核心逻辑设计

#### 4.4.1 订单状态机

**状态定义**：
- CREATED：已创建
- COMPLETED：已完成
- FAILED：失败

**状态流转**：
```
CREATED ──成功──▶ COMPLETED
   │
   └──失败──▶ FAILED
```

**状态流转规则**：
- CREATED → COMPLETED：监听到InventoryDeductedEvent
- CREATED → FAILED：监听到OrderFailedEvent
- COMPLETED、FAILED为终态，不可再流转

**实现代码**：
```java
public class Order {
    public void markAsCompleted() {
        if (this.status != OrderStatus.CREATED) {
            throw new IllegalStateException("订单状态不是CREATED，无法标记为完成");
        }
        this.status = OrderStatus.COMPLETED;
        this.completedAt = LocalDateTime.now();
    }
    
    public void markAsFailed(String reason) {
        if (this.status != OrderStatus.CREATED) {
            throw new IllegalStateException("订单状态不是CREATED，无法标记为失败");
        }
        this.status = OrderStatus.FAILED;
        this.failureReason = reason;
    }
}
```

#### 4.4.2 乐观锁重试机制

**应用场景**：
- 用户余额扣减
- 商家余额增加
- 库存扣减

**重试策略**：
- 最大重试次数：3次
- 退避算法：指数退避（100ms, 200ms, 400ms）
- 最后一次失败：抛出OptimisticLockException

**实现代码**：
```java
int maxRetries = 3;
for (int retryCount = 0; retryCount < maxRetries; retryCount++) {
    try {
        int updatedRows = mapper.deductBalanceWithVersion(userId, amount, version);
        if (updatedRows == 0) {
            if (retryCount < maxRetries - 1) {
                long waitTime = (long) Math.pow(2, retryCount) * 100;
                Thread.sleep(waitTime);
                continue;
            } else {
                throw new OptimisticLockException("并发冲突，已重试" + maxRetries + "次");
            }
        }
        return; // 成功退出
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RuntimeException("重试被中断", e);
    }
}
```

## 五、关键技术点设计

### 5.1 并发控制

#### 5.1.1 乐观锁

**原理**：
- 在表中添加version字段
- 更新时检查版本号：`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?`
- 如果受影响行数为0，说明被其他事务修改

**适用场景**：
- 读多写少
- 冲突概率低
- 高并发场景

**实现示例**：
```sql
-- 扣减余额（乐观锁）
UPDATE user_account
SET balance = balance - #{amount},
    version = version + 1,
    updated_at = NOW()
WHERE user_id = #{userId}
  AND version = #{version}
  AND balance >= #{amount}
```

---

#### 5.1.2 数据库行锁

**原理**：
- 查询时使用`SELECT ... FOR UPDATE`锁定行
- 其他事务等待锁释放

**适用场景**：
- 写多读少
- 冲突概率高
- 需要强一致性

**实现示例**：
```java
// 查询并锁定行
UserAccount account = userAccountMapper.selectForUpdate(userId);

// 更新余额
account.recharge(amount);
userAccountMapper.update(account);
```

**注意事项**：
- 设置合理的超时时间（innodb_lock_wait_timeout = 5s）
- 避免长时间持有锁
- 统一资源访问顺序，防止死锁

## 十一、总结与展望

### 11.1 设计亮点

1. ✅ **DDD领域驱动设计**：清晰划分限界上下文，聚合根保证数据一致性
2. ✅ **事件驱动架构**：模块解耦，异步处理，提升并发性能
3. ✅ **分层限流策略**：接口级+用户级双层保护，零代码侵入
4. ✅ **乐观锁重试机制**：高并发场景下保证数据一致性
5. ✅ **完善补偿机制**：失败自动回滚，T+1对账保证最终一致
6. ✅ **配置化管理**：限流规则、业务参数均可配置，易于调整
7. ✅ **可扩展性强**：新增业务只需添加监听器，符合开闭原则

---

### 11.2 待优化项

1. **事件持久化**：当前使用Spring Event，生产环境建议迁移到RabbitMQ/Kafka
2. **缓存引入**：高频查询场景可引入Redis缓存
3. **监控告警**：补充Prometheus + Grafana监控体系
4. **链路追踪**：引入SkyWalking或Zipkin追踪事件链路
5. **API文档**：集成Swagger/OpenAPI自动生成接口文档
6. **认证鉴权**：补充JWT Token认证和Spring Security权限控制
