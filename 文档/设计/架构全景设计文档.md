## 一、业务与需求分析

### 1.1 业务背景

本系统是一个面向技术面试的商品交易演示系统，旨在展示系统设计能力和编码水平。系统实现用户与商家之间的完整交易流程，包括账户充值、商品管理、下单购买、资金结算等核心功能。

**产品定位**：技术演示项目（非生产环境）  
**目标用户**：面试官（评估设计能力和代码质量）  
**核心价值**：展示DDD领域驱动设计、清晰的代码结构、高质量的单元测试

### 1.2 用户角色

| 角色 | 描述 | 核心诉求 |
|-----|------|---------|
| 普通用户 | 购买商品的用户 | 充值便捷、下单流畅、数据准确 |
| 商家 | 提供商品的商家 | 库存管理方便、收益清晰、对账准确 |
| 系统管理员 | 运维人员 | 系统稳定、监控完善、异常可追溯 |

### 1.3 核心业务流程

#### 流程1：用户充值流程
```
用户发起充值 → 验证金额合法性 → 检查幂等性 → 更新余额 → 记录流水 → 返回结果
```

**关键点**：
- 充值金额范围：0.01 ~ 10,000元
- 必须支持幂等性（requestId去重）
- 强一致性保证（本地事务）

#### 流程2：商家添加库存流程
```
商家发起添加 → 验证SKU格式 → 验证价格/数量 → 判断SKU是否存在 → 创建或累加 → 返回结果
```

**关键点**：
- SKU格式：`^[A-Z0-9_]+$`
- 价格精度：2位小数
- 同一商家下SKU唯一

#### 流程3：用户下单购买流程（核心）
```
用户发起下单 → 开启事务 → 验证库存和余额 → 创建订单 → 扣减用户余额 → 扣减库存 
→ 增加商家余额 → 记录流水 → 更新订单状态 → 提交事务 → 返回结果
```

**关键点**：
- **所有操作在一个数据库事务中完成**
- 使用乐观锁防止并发冲突
- 任一失败则全部回滚（ACID）
- 订单状态：CREATED → COMPLETED 或 FAILED

#### 流程4：商家每日结算对账流程
```
定时任务触发（每天02:00） → 遍历商家 → 统计销售总额 → 统计收款总额 
→ 对比金额 → 生成对账记录 → 不一致则告警
```

**关键点**：
- 对账日期：自然日（00:00:00 - 23:59:59）
- 对账容忍度：0.00元（必须完全一致）
- 告警方式：日志记录（可扩展）

## 二、领域建模（核心）

### 2.1 限界上下文划分

采用DDD领域驱动设计，将系统划分为三个限界上下文，通过**包路径**进行物理隔离：

```
com.example.tradesystem
├── user（用户上下文）
├── merchant（商家上下文）
└── trade（交易上下文）
```

#### 2.1.1 用户上下文（User Context）

**职责边界**：
- 管理用户预存账户
- 处理账户充值
- 管理充值记录

**不包含的职责**：
- ❌ 订单管理（属于交易上下文）
- ❌ 商品管理（属于商家上下文）

#### 2.1.2 商家上下文（Merchant Context）

**职责边界**：
- 管理商家账户
- 管理商品库存（SKU维度）
- 处理库存添加
- 执行每日结算对账

**不包含的职责**：
- ❌ 订单管理（属于交易上下文）
- ❌ 用户账户管理（属于用户上下文）

#### 2.1.3 交易上下文（Trade Context）

**职责边界**：
- 管理订单生命周期
- 协调交易流程（调用用户和商家服务）
- 订单查询

**不包含的职责**：
- ❌ 直接操作账户余额（由用户/商家上下文处理）
- ❌ 直接操作库存（由商家上下文处理）

### 2.2 聚合根设计

#### 2.2.1 用户上下文聚合根

**聚合根：UserAccount（用户账户）**

```java
package com.example.tradesystem.user.domain.model;

public class UserAccount {

    private LocalDateTime createdAt;  // 创建时间
    private LocalDateTime updatedAt;  // 更新时间
    
    // 业务方法

        // 充值逻辑
    }
```

**不变式约束**：
- `balance.amount >= 0`（余额不能为负）
- `amount > 0`（操作金额必须大于0）

**实体：RechargeRecord（充值记录）**


**值对象：Money（金额）**

```java
package com.example.tradesystem.user.domain.model;

public class Money {
    private final BigDecimal amount;  // 金额（精度2位小数）
    private final String currency;    // 货币类型（CNY）
    
    public Money add(Money other) {
        return new Money(this.amount.add(other.amount), this.currency);
    }
    
    public Money subtract(Money other) {
        return new Money(this.amount.subtract(other.amount), this.currency);
    }
    
    public boolean isPositive() {
        return amount.compareTo(BigDecimal.ZERO) > 0;
    }
}
```

#### 2.2.3 交易上下文聚合根

**聚合根：Order（订单）**

```java
package com.example.tradesystem.trade.domain.model;

public class Order {
    private String orderId;                // 订单ID（UUID）
    private Long userId;                   // 用户ID
    private Long merchantId;               // 商家ID
    private OrderStatus status;            // 订单状态
    private List<OrderItem> items;         // 订单项列表
    private Money totalAmount;             // 订单总金额
    private LocalDateTime createTime;      // 创建时间
    private LocalDateTime completeTime;    // 完成时间
    private Integer version;               // 乐观锁版本号
    
    // 业务方法
    public void calculateTotalAmount() {
        // 计算总金额 = Σ(订单项小计)
    }
    
    public void markAsCompleted() {
        if (this.status != OrderStatus.CREATED) {
            throw new IllegalStateException("只有已创建的订单才能完成");
        }
        this.status = OrderStatus.COMPLETED;
        this.completeTime = LocalDateTime.now();
    }
    
    public void markAsFailed() {
        this.status = OrderStatus.FAILED;
    }
}
```

**不变式约束**：
- `items` 不为空
- `totalAmount = Σ(items.subtotal)`
- 订单创建后不可修改 `items`
- 状态只能单向流转：CREATED → COMPLETED 或 FAILED

**值对象：OrderItem（订单项）**

```java
package com.example.tradesystem.trade.domain.model;

public class OrderItem {
    private Long itemId;                 // 项ID
    private String sku;                  // 商品SKU
    private String productName;          // 商品名称
    private Integer quantity;            // 购买数量
    private Money unitPrice;             // 单价
    private Money subtotal;              // 小计
    
    public OrderItem(String sku, String productName, Integer quantity, Money unitPrice) {
        this.sku = sku;
        this.productName = productName;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
        this.subtotal = unitPrice.multiply(quantity);
    }
}
```

**不变式约束**：
- `quantity > 0`
- `unitPrice.amount > 0`
- `subtotal = quantity × unitPrice`
- **不可变性**（Immutable）

### 2.3 领域服务

#### 2.3.1 OrderService（订单服务）

```java
package com.example.tradesystem.trade.application.service;

@Service
@Transactional
public class OrderService {
    
    @Autowired
    private UserRepository userRepository;
    
    @Autowired
    private InventoryRepository inventoryRepository;
    
    @Autowired
    private MerchantRepository merchantRepository;
    
    @Autowired
    private OrderRepository orderRepository;
    
    /**
     * 创建订单（核心业务逻辑）
     */
    public Order createOrder(CreateOrderRequest request) {
        // 1. 查询用户账户（带乐观锁）
        UserAccount user = userRepository.findByIdForUpdate(request.getUserId());
        
        // 2. 查询商品库存（带乐观锁）
        ProductInventory inventory = inventoryRepository.findBySkuForUpdate(request.getSku());
        
        // 3. 验证库存充足
        if (!inventory.isStockSufficient(request.getQuantity())) {
            throw new InsufficientStockException("库存不足");
        }
        
        // 4. 计算订单金额
        Money totalAmount = inventory.getPrice().multiply(request.getQuantity());
        
        // 5. 验证余额充足
        if (user.getBalance().compareTo(totalAmount) < 0) {
            throw new InsufficientBalanceException("余额不足");
        }
        
        // 6. 创建订单
        Order order = new Order(request.getUserId(), request.getMerchantId(), totalAmount);
        OrderItem item = new OrderItem(
            inventory.getSku(),
            inventory.getProductName(),
            request.getQuantity(),
            inventory.getPrice()
        );
        order.addItem(item);
        
        // 7. 执行业务操作（在同一事务中）
        user.deduct(totalAmount);                    // 扣减用户余额
        inventory.deductStock(request.getQuantity()); // 扣减库存
        MerchantAccount merchant = merchantRepository.findById(request.getMerchantId());
        merchant.credit(totalAmount);                // 增加商家余额
        
        // 8. 保存数据
        order.markAsCompleted();
        orderRepository.save(order);
        userRepository.save(user);
        inventoryRepository.save(inventory);
        merchantRepository.save(merchant);
        
        // 9. 记录流水
        recordTransaction(order, user, merchant, inventory);
        
        return order;
    }
}
```

## 三、系统架构设计

### 3.1 架构选型

**架构模式**：单体应用（Monolithic）+ DDD模块化设计

**选型理由**：
1. ✅ 符合需求："一个能本地运行的Spring Boot应用程序"
2. ✅ 简单可靠：无需配置复杂的微服务基础设施
3. ✅ 易于测试：单元测试和集成测试更简单
4. ✅ 易于演示：面试时启动一个应用即可
5. ✅ 保留扩展性：通过包结构划分边界，后续可轻松拆分为微服务

### 3.4 模块间依赖关系

```
trade（交易上下文）
  ↓ 依赖
user（用户上下文） + merchant（商家上下文）

user 和 merchant 之间无直接依赖
```

**依赖规则**：
- ✅ trade 可以调用 user 和 merchant 的 Repository
- ❌ user 和 merchant 不能互相调用
- ❌ 上层不能依赖下层的具体实现（依赖倒置）

### 4.2 中间件选型

| 中间件 | 是否使用 | 说明 |
|-------|---------|------|
| Redis | ❌ 不使用 | 增加复杂度，不符合"本地运行"要求 |
| RabbitMQ | ❌ 不使用 | 同步事务不需要消息队列 |

| Elasticsearch | ❌ 不使用 | 查询需求简单，MySQL足够 |

**选型理由**：
- 需求明确要求"一个能本地运行的Spring Boot应用程序"
- 引入中间件会增加部署复杂度
- 本地事务已经能保证数据一致性
- 面试场景下，展示代码质量比展示中间件更重要

### 4.3 关键技术决策

#### 决策1：为什么不用微服务？

**原因**：
1. 需求明确要求"一个应用程序"
2. 微服务需要服务注册发现、配置中心、网关等基础设施
3. 面试场景下，时间有限，应聚焦核心业务逻辑
4. 通过DDD包结构划分，保留了未来拆分的可能性

#### 决策2：为什么不用Redis分布式锁？

**原因**：
1. 单体应用不需要分布式锁
2. 数据库乐观锁已经能解决并发问题
3. 减少外部依赖，简化部署

#### 决策3：为什么不用MQ异步处理？

**原因**：
1. 需求中的交易流程是原子的，需要同步完成
2. 本地事务能保证ACID，不需要最终一致性
3. 异步处理会增加复杂度（补偿机制、幂等性等）

### 7.1 高并发设计

#### 7.1.1 并发控制方案

**方案1：乐观锁（推荐）**

```java
// 实体中添加version字段
@Entity
public class UserAccount {
    @Version
    private Integer version;
}

// 更新时自动检查版本号
@Modifying
@Query("UPDATE UserAccount SET balance = :balance, version = version + 1 WHERE userId = :userId AND version = :version")
int updateBalance(@Param("userId") Long userId, @Param("balance") BigDecimal balance, @Param("version") Integer version);
```

**优点**：
- 无锁竞争，性能好
- 不会死锁
- 适合读多写少场景

**缺点**：
- 高并发下可能频繁重试
- 需要客户端处理重试逻辑

---

**方案2：数据库行锁**

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT u FROM UserAccount u WHERE u.userId = :userId")
UserAccount findByIdForUpdate(@Param("userId") Long userId);
```

**优点**：
- 强一致性保证
- 适合写多场景

**缺点**：
- 可能产生死锁
- 性能较差

#### 7.1.2 防超卖机制

**实现方式**：
```java
@Transactional
public Order createOrder(CreateOrderRequest request) {
    // 1. 查询库存（带锁）
    ProductInventory inventory = inventoryRepository.findBySkuForUpdate(request.getSku());
    
    // 2. 验证库存
    if (inventory.getStockQuantity() < request.getQuantity()) {
        throw new InsufficientStockException("库存不足");
    }
    
    // 3. 扣减库存
    inventory.deductStock(request.getQuantity());
    
    // 4. 其他操作...
}
```

**保证**：
- 数据库事务隔离级别：READ_COMMITTED
- 使用行锁或乐观锁
- 不会出现超卖

#### 7.1.3 限流策略（可选）

**基于Token Bucket的简单限流**：

```java
@Component
public class RateLimiter {
    private final Map<String, AtomicInteger> counters = new ConcurrentHashMap<>();
    private final int maxRequestsPerSecond = 100;
    
    public boolean allowRequest(String key) {
        AtomicInteger counter = counters.computeIfAbsent(key, k -> new AtomicInteger(0));
        return counter.incrementAndGet() <= maxRequestsPerSecond;
    }
}
```

### 7.3 一致性设计

#### 7.3.1 事务一致性（ACID）

**实现方式**：
```java
@Service

```

**保证**：
- ✅ 原子性（Atomicity）：事务中的所有操作要么全部成功，要么全部失败
- ✅ 一致性（Consistency）：事务前后数据保持一致
- ✅ 隔离性（Isolation）：事务之间互不干扰
- ✅ 持久性（Durability）：事务提交后数据永久保存
