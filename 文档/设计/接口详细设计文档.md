## 一、概述

### 1.1 设计目标

本文档定义了商品交易系统的REST API接口规范，包括：
- **用户模块**：账户充值、余额查询、充值记录查询
- **商家模块**：库存管理、商品信息查询、账户查询、对账记录查询
- **交易模块**：订单创建、订单详情查询、订单列表查询

### 1.2 设计规范

遵循**阿里巴巴Java开发手册**和**RESTful API设计规范**：

1. **资源命名**：使用名词复数形式（如`/orders`、`/users`）
2. **HTTP方法**：
   - GET：查询资源
   - POST：创建资源
   - PUT：更新资源
   - DELETE：删除资源
3. **版本控制**：URL中包含版本号（`/api/v1/...`）
4. **统一响应格式**：所有接口返回统一的JSON结构
5. **状态码规范**：正确使用HTTP状态码
6. **参数校验**：使用Bean Validation校验输入参数
7. **幂等性**：关键接口支持幂等性（如充值）

## 二、统一响应格式

### 2.1 成功响应

```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": "2026-05-02T10:30:00"
}
```

### 2.2 错误响应

```json
{
  "code": 400,
  "message": "充值金额不能为0",
  "data": null,
  "timestamp": "2026-05-02T10:30:00"
}
```

### 2.3 响应字段说明

| 字段名 | 类型 | 说明 |
|-------|------|------|
| code | Integer | 响应码（200=成功，400=参数错误，404=资源不存在，429=触发限流，500=系统异常） |
| message | String | 响应消息（成功时为"success"，失败时为错误描述） |
| data | Object | 响应数据（成功时返回业务数据，失败时为null） |
| timestamp | String | 响应时间（ISO 8601格式） |

## 三、错误码设计

| 错误码 | HTTP状态码 | 说明 | 使用场景 |
|-------|-----------|------|---------|
| 200 | 200 | 成功 | 请求成功处理 |
| 400 | 400 | 请求参数错误 | 参数校验失败、业务规则违反 |

| 429 | 429 | 触发限流 | 请求频率过高 |

## 五、用户模块接口

### 5.1 账户充值

#### 5.1.1 接口基本信息

| 项目 | 内容 |
|-----|------|
| 接口名称 | 账户充值 |
| 接口描述 | 用户向预存账户充值，支持人民币一种货币 |
| 请求类型 | POST |
| 接口地址 | `/api/v1/users/{userId}/accounts/recharge` |
| 权限要求 | 无（技术演示项目） |
| 幂等性 | ✅ 支持（通过requestId保证） |
| 限流策略 | 接口级200 TPS，用户级5 TPS |

#### 5.1.2 请求参数

**路径参数**：

| 参数名 | 类型 | 必填 | 说明 | 示例 |
|-------|------|------|------|------|
| userId | Long | ✅ | 用户ID | 1001 |

**请求体（Request Body）**：

| 参数名 | 类型 | 必填 | 校验规则 | 说明 | 示例 |
|-------|------|------|---------|------|------|
| amount | BigDecimal | ✅ | 范围：0.01~10000.00，精度2位小数 | 充值金额（单位：元） | 100.00 |
| requestId | String | ✅ | 长度≤64，全局唯一 | 请求ID（客户端生成，保证幂等性） | REQ_20260502_001 |

**请求示例**：

```json
POST /api/v1/users/1001/accounts/recharge
Content-Type: application/json

{
  "amount": 100.00,
  "requestId": "REQ_20260502_001"
}
```

#### 5.1.3 响应参数

**成功响应（HTTP 200）**：

| 参数名 | 类型 | 说明 | 示例 |
|-------|------|------|------|
| code | Integer | 响应码 | 200 |
| message | String | 响应消息 | "success" |
| data.userId | Long | 用户ID | 1001 |
| data.balance | BigDecimal | 充值后余额（单位：元） | 600.00 |
| data.rechargeId | String | 充值ID | RCH_20260502_001 |

**响应示例**：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "userId": 1001,
    "balance": 600.00,
    "rechargeId": "RCH_20260502_001"
  },
  "timestamp": "2026-05-02T10:30:00"
}
```

**错误响应（HTTP 400）**：

| 场景 | 错误码 | 错误消息 |
|-----|-------|---------|
| 充值金额为0或负数 | 400 | "充值金额必须大于0" |
| 充值金额超过上限 | 400 | "充值金额超出限制" |
| requestId重复 | 400 | "请求已处理，请勿重复提交" |

**错误响应示例**：

```json
{
  "code": 400,
  "message": "充值金额必须大于0",
  "data": null,
  "timestamp": "2026-05-02T10:30:00"
}
```

## 八、接口设计规范总结

### 8.1 RESTful API 设计原则

1. **资源命名**：
   - 使用名词复数形式：`/orders`、`/users`、`/merchants`
   - 避免动词：不使用`/getOrders`、`/createOrder`

2. **HTTP方法语义**：
   - GET：查询资源（安全、幂等）
   - POST：创建资源
   - PUT：更新资源（完整替换）
   - PATCH：部分更新资源（本系统未使用）
   - DELETE：删除资源（本系统未使用）

3. **版本控制**：
   - URL中包含版本号：`/api/v1/...`
   - 便于后续迭代和兼容旧版本

4. **统一响应格式**：
   - 所有接口返回相同的JSON结构
   - 包含code、message、data、timestamp字段

5. **状态码规范**：
   - 200：成功
   - 400：请求参数错误
   - 404：资源不存在
   - 429：触发限流
   - 500：服务器内部错误

---

### 8.2 参数校验规范

1. **必填参数校验**：
   - 使用Bean Validation注解（@NotNull、@NotBlank）
   - 在Controller层统一校验

2. **格式校验**：
   - SKU格式：正则表达式`^[A-Z0-9_]+$`
   - 日期格式：ISO 8601（YYYY-MM-DD）
   - 金额精度：DECIMAL(10,2)

3. **范围校验**：
   - 充值金额：0.01~10000.00
   - 库存数量：1~9999
   - 购买数量：1~99

4. **业务规则校验**：
   - 余额充足性
   - 库存充足性
   - 幂等性检查

---

### 8.3 幂等性设计

1. **充值接口幂等性**：
   - 通过requestId唯一索引保证
   - 相同requestId多次请求只处理一次
   - 第二次请求直接返回第一次的结果

2. **查询接口天然幂等**：
   - GET请求不修改数据
   - 多次调用返回相同结果

3. **创建订单非幂等**：
   - 每次调用都会创建新订单
   - 前端应避免重复提交

---

### 8.4 限流策略

1. **分层限流**：
   - 全局限流：1000 TPS（可选）
   - 接口级限流：根据不同接口设置不同阈值
   - 用户级限流：防止单个用户恶意刷单

2. **限流实现**：
   - 自定义注解@RateLimit
   - HandlerInterceptor拦截器
   - Guava RateLimiter令牌桶算法

3. **限流响应**：
   - HTTP状态码：429 Too Many Requests
   - 响应头：Retry-After（告知客户端何时可以重试）
   - 响应体：友好的错误提示

---

### 8.5 异常处理规范

1. **业务异常**：
   - 返回400状态码
   - 明确的错误消息
   - 不暴露内部实现细节

2. **系统异常**：
   - 返回500状态码
   - 记录详细日志
   - 返回通用错误提示

3. **全局异常处理器**：
   - 使用@ControllerAdvice统一处理
   - 分类处理不同类型的异常
   - 返回统一的错误响应格式
