## 一、系统概述

### 1.1 系统背景

本系统是一个完整的商品交易系统，实现用户与商家之间的商品交易流程，包括用户充值、商品库存管理、下单购买、资金结算等核心功能。系统采用DDD领域驱动设计思想，通过事件驱动架构实现模块解耦和高并发优化。

### 1.2 设计目标

**业务目标**：
- 实现完整的商品交易闭环：充值 → 上架 → 下单 → 支付 → 结算
- 保证交易的准确性和一致性，避免超卖、重复扣款等问题
- 提供清晰的账务对账机制，确保财务数据准确

**技术目标**：
- 采用DDD领域驱动设计，合理划分业务边界
- 实现高内聚低耦合的模块化设计
- 核心代码单元测试覆盖率达到80%以上
- 具备良好的可扩展性，支持后续功能迭代
- 支持500 TPS并发订单处理能力

### 1.3 适用范围

本文档适用于：
- 系统开发人员：理解系统整体架构和模块职责
- 测试人员：制定测试策略和用例
- 运维人员：了解系统部署和监控要求
- 技术面试官：评估系统设计能力

## 二、模块划分与职责

### 2.1 模块划分

系统采用单体应用 + DDD模块化架构，划分为三个限界上下文（Bounded Context）：

```
com.example.tradesystem
├── user-context（用户上下文）
├── merchant-context（商家上下文）
└── trade-context（交易上下文）
```

### 2.2 模块职责与边界

#### 2.2.1 用户上下文（User Context）

**包路径**：`com.example.tradesystem.user`

**核心职责**：
- 管理用户预存账户（余额查询、更新）
- 处理账户充值（充值验证、余额增加、流水记录）
- 监听订单事件并执行余额扣减
- 处理退款操作（订单失败时的补偿）

**聚合根**：
- `UserAccount`：用户账户（userId, balance, version）

**实体**：
- `RechargeRecord`：充值记录（rechargeId, userId, amount, status）

**发布的领域事件**：
- `UserBalanceDeductedEvent`：用户余额扣减成功
- `UserBalanceRefundedEvent`：用户余额退款成功

**监听的领域事件**：
- `OrderCreatedEvent`：订单创建成功，需要扣减余额
- `OrderFailedEvent`：订单失败，需要退款

**对外接口**：
- `POST /api/v1/users/{userId}/accounts/recharge` - 账户充值
- `GET /api/v1/users/{userId}/accounts` - 查询余额
- `GET /api/v1/users/{userId}/accounts/recharges` - 查询充值记录

---

#### 2.2.2 商家上下文（Merchant Context）

**包路径**：`com.example.tradesystem.merchant`

**核心职责**：
- 管理商家账户（余额查询、更新）
- 管理商品库存（SKU维度，添加/更新库存）
- 监听订单事件并执行库存扣减、商家余额增加
- 执行每日结算对账任务
- 处理库存恢复操作（订单失败时的补偿）

**聚合根**：
- `ProductInventory`：商品库存（sku, stockQuantity, price, version）
- `MerchantAccount`：商家账户（merchantId, balance, totalIncome, version）

**实体**：
- `MerchantCreditRecord`：收款记录（creditId, merchantId, amount, orderId）
- `SettlementRecord`：对账记录（settlementId, merchantId, date, status）

**发布的领域事件**：
- `InventoryDeductedEvent`：库存扣减成功
- `StockRestoredEvent`：库存恢复成功

**监听的领域事件**：
- `UserBalanceDeductedEvent`：用户余额已扣减，需要扣减库存
- `OrderFailedEvent`：订单失败，需要恢复库存

**对外接口**：
- `POST /api/v1/merchants/{merchantId}/products/{sku}/stock` - 添加/更新库存
- `GET /api/v1/merchants/{merchantId}/products/{sku}` - 查询商品信息
- `GET /api/v1/merchants/{merchantId}/accounts` - 查询商家账户
- `GET /api/v1/merchants/{merchantId}/settlements` - 查询对账记录

---

#### 2.2.3 交易上下文（Trade Context）

**包路径**：`com.example.tradesystem.trade`

**核心职责**：
- 管理订单生命周期（创建、状态流转）
- 协调交易流程（验证、发布事件）
- 监听所有事件并更新订单状态
- 提供订单查询服务

**聚合根**：
- `Order`：订单（orderId, userId, merchantId, status, totalAmount）

**实体**：
- `OrderItem`：订单项（orderItemId, orderId, sku, quantity, unitPrice）

**发布的领域事件**：
- `OrderCreatedEvent`：订单创建成功
- `OrderCompletedEvent`：订单完成
- `OrderFailedEvent`：订单失败

**监听的领域事件**：
- `InventoryDeductedEvent`：库存已扣减，更新订单为COMPLETED
- 任何失败事件：更新订单为FAILED

**对外接口**：
- `POST /api/v1/orders` - 创建订单
- `GET /api/v1/orders/{orderId}` - 查询订单详情
- `GET /api/v1/users/{userId}/orders` - 查询用户订单列表

### 2.3 模块依赖关系

```
┌─────────────────┐
│  Trade Context  │ ← 核心协调者，发布OrderCreatedEvent
└────────┬────────┘
         │ 发布事件
         ▼
┌─────────────────┐     ┌──────────────────┐
│  User Context   │────▶│ Merchant Context │
│  (扣减余额)      │     │  (扣减库存+加余额) │
└─────────────────┘     └──────────────────┘
         │                      │
         └────── 发布事件 ──────┘
                ▼
         ┌─────────────────┐
         │  Trade Context  │ ← 更新订单状态
         └─────────────────┘
```

**依赖原则**：
- 模块间通过领域事件通信，不直接调用
- 事件发布者不依赖事件监听者
- 每个模块独立事务，保证最终一致性

## 三、核心业务流程

### 3.1 用户充值流程（同步）

**流程说明**：用户向预存账户充值，立即更新余额。

**主流程**：
```
1. 接收充值请求（userId, amount, requestId）
2. 验证参数合法性（金额范围、格式）
3. 检查幂等性（requestId去重）
4. 开启事务
5. 查询用户账户（SELECT FOR UPDATE）
6. 更新余额（balance = balance + amount）
7. 记录充值流水
8. 提交事务
9. 返回充值结果和最新余额
```

**异常流程**：
- 充值金额为0或负数 → 返回400错误
- 充值金额超过上限 → 返回400错误
- 用户不存在 → 自动创建账户
- 数据库异常 → 事务回滚，返回500错误

**关键设计点**：
- **幂等性保证**：通过requestId唯一索引防止重复充值
- **并发安全**：使用SELECT FOR UPDATE锁定账户行
- **事务范围**：仅包含余额更新和流水记录，快速提交

---

### 3.2 商家添加库存流程（同步）

**流程说明**：商家向库存中添加商品，支持新增和累加。

**主流程**：
```
1. 接收添加库存请求（merchantId, sku, quantity, price）
2. 验证参数合法性（SKU格式、价格、数量）
3. 开启事务
4. 查询库存记录（SELECT FOR UPDATE）
5. 判断是否存在
   ├─ 存在：累加库存数量，可选更新价格
   └─ 不存在：创建新库存记录
6. 提交事务
7. 返回最新库存信息
```

**异常流程**：
- SKU格式错误 → 返回400错误
- 价格或数量不合法 → 返回400错误
- 并发添加 → 行锁等待，超时后重试

**关键设计点**：
- **SKU唯一性**：同一商家下SKU唯一（联合唯一索引）
- **并发安全**：使用SELECT FOR UPDATE锁定库存行
- **累加逻辑**：已存在SKU时累加数量，避免覆盖

---

### 3.3 用户下单购买流程（事件驱动 - 核心）

**流程说明**：采用事件驱动架构，将长事务拆分为4个短事务，提升并发性能。

#### 3.3.1 五阶段详解

| 阶段 | 模块 | 操作 | 事务 | 事件 |
|-----|------|------|------|------|
| **阶段0** | Trade Context | 限流检查（接口级+用户级） | 无 | 无 |
| **阶段1** | Trade Context | 验证库存和余额、创建订单(CREATED)、发布OrderCreatedEvent | 本地事务 | OrderCreatedEvent |
| **阶段2** | User Context | 监听OrderCreatedEvent、扣减用户余额、记录扣款流水、发布UserBalanceDeductedEvent | 独立事务 | UserBalanceDeductedEvent |
| **阶段3** | Merchant Context | 监听UserBalanceDeductedEvent、扣减库存、增加商家余额、记录收款流水、发布InventoryDeductedEvent | 独立事务 | InventoryDeductedEvent |
| **阶段4** | Trade Context | 监听InventoryDeductedEvent、更新订单为COMPLETED、发布OrderCompletedEvent | 独立事务 | OrderCompletedEvent |

**时序图**：
```
用户          Trade Context       User Context      Merchant Context
 │                  │                  │                  │
 │──创建订单──────▶│                  │                  │
 │                  │──验证库存余额──│                  │
 │                  │──创建订单──────│                  │
 │                  │──发布事件─────│                  │
 │◀──返回订单ID───│                  │                  │
 │                  │                  │                  │
 │                  │──异步触发─────▶│                  │
 │                  │                  │──扣减余额──────│
 │                  │                  │──发布事件─────│
 │                  │                  │                  │
 │                  │                  │──异步触发─────▶│
 │                  │                  │                  │──扣减库存
 │                  │                  │                  │──增加余额
 │                  │                  │                  │──发布事件
 │                  │                  │                  │
 │                  │◀──异步触发──────│                  │
 │                  │──更新订单状态──│                  │
 │                  │                  │                  │
```

#### 3.3.2 关键设计点

**限流保护**：
- 阶段0进行接口级（600 TPS）和用户级（10 TPS）限流，防止系统过载
- 使用Guava RateLimiter实现令牌桶算法
- 零代码侵入：通过拦截器 + @RateLimit注解实现

**缩短事务持有锁时间**：
- 每个阶段独立事务，避免长时间锁定资源
- 阶段1仅验证和创建订单，不涉及余额和库存更新
- 事务持有锁时间控制在100ms以内（P95）

**异步解耦**：
- 通过Spring Event事件总线解耦领域间依赖
- 使用@TransactionalEventListener(phase = AFTER_COMMIT)确保事务提交后发布事件
- 领域间无直接调用，降低耦合度

**最终一致性**：
- 通过事件链保证数据最终一致
- 每个阶段独立提交，即使后续阶段失败，前序数据已持久化
- 通过补偿机制处理失败场景

**快速响应**：
- 阶段1完成后立即返回订单ID，用户体验好
- 阶段1响应时间 < 50ms（P95）
- 完整流程处理时间 < 2s（P95）

---

#### 3.3.3 异常补偿流程

**补偿场景**：
- 阶段2失败（余额扣减失败）→ 无需补偿（订单未扣款）
- 阶段3失败（库存扣减失败）→ 触发退款 + 恢复库存
- 阶段4失败（订单状态更新失败）→ 不影响数据一致性，可人工介入

**补偿流程**：
```
1. 任一阶段失败 → 发布OrderFailedEvent（包含失败阶段标识）
2. User Context监听 → 判断是否需要退款 → 执行退款操作
3. Merchant Context监听 → 判断是否需要恢复库存 → 执行恢复操作
4. Trade Context监听 → 更新订单状态为FAILED
5. 记录异常日志，必要时人工介入
```

**关键设计点**：
- **失败阶段标识**：OrderFailedEvent携带failedStage字段，区分失败位置
- **条件补偿**：根据失败阶段判断是否需要执行补偿操作
- **幂等性**：补偿操作支持重复执行，不会产生副作用
- **异常记录**：所有失败记录到exception_record表，便于追踪

### 3.4 商家每日结算对账流程

**流程说明**：每天凌晨02:00自动执行对账任务，对比销售总额和收款总额。

**主流程**：
```
1. 定时任务触发（每天02:00，选择低峰期避免影响正常业务）
2. 遍历所有商家
3. 对每个商家执行：
   ├─ 统计昨日销售总额：Σ(已售数量 × 单价)，按SKU汇总
   ├─ 查询昨日商家账户增加金额：从收款流水中汇总
   ├─ 对比两个金额
   │   ├─ 一致：对账状态 = MATCHED
   │   └─ 不一致：对账状态 = MISMATCHED，记录差异金额
   ├─ 生成对账记录
   └─ 如果不一致，发送告警通知（日志记录）
4. 记录任务执行日志
```

**关键设计点**：
- **低峰期执行**：选择凌晨02:00避免影响正常业务
- **容错处理**：单个商家对账失败不影响其他商家
- **告警机制**：不一致时记录日志，可扩展为邮件/短信告警
- **手动重对账**：支持手动触发重新对账

### 6.3 关键技术决策

#### 决策1：为什么用事件驱动？

**优势**：
- 领域间解耦：通过事件通信，不直接调用
- 异步处理：提升响应速度
- 易于扩展：新增业务只需添加监听器
- 高并发优化：缩短事务持有锁时间

**劣势**：
- 调试复杂：事件链路长
- 最终一致性：需要补偿机制

---

#### 决策2：如何保证事件不丢失？

**问题分析**：
Spring Event是内存中的事件机制，应用重启会导致未处理的事件丢失。例如：
- 如果阶段1发布OrderCreatedEvent后立即重启，后续阶段永远不会执行
- 订单将永远停留在CREATED状态，用户余额已扣减但库存未扣减
- 造成数据不一致，影响用户体验和账务准确性

**方案**：
1. **事务绑定**：使用`@TransactionalEventListener(phase = AFTER_COMMIT)`确保事务提交后才发布事件
   - 避免事务回滚后事件仍被消费的问题
   
2. **事件持久化（推荐）**：关键事件保存到`domain_event_record`表，支持事件回溯和重放
   ```java
   // 在发布事件前持久化
   eventRecordRepository.save(new EventRecord(event.getEventId(), "PENDING"));
   eventPublisher.publishEvent(event);
   
   // 监听器处理完成后更新状态
   eventRecordRepository.updateStatus(event.getEventId(), "PROCESSED");
   
   // 定时任务扫描PENDING状态的事件，超过阈值则重发
   @Scheduled(fixedDelay = 60000) // 每分钟检查一次
   public void retryPendingEvents() {
       List<EventRecord> pendingEvents = eventRecordRepository.findPendingEvents();
       for (EventRecord record : pendingEvents) {
           if (record.getCreatedAt().plusMinutes(5).isBefore(LocalDateTime.now())) {
               log.warn("事件处理超时，准备重发: eventId={}", record.getEventId());
               // 重发逻辑...
           }
       }
   }
   ```
   
3. **重试机制**：监听器内部捕获异常，最多重试3次（指数退避）
   - 详见代码示例中的重试逻辑
   
4. **对账补偿**：T+1对账发现不一致，人工介入处理
   - 每天凌晨02:00执行对账任务
   - 对比订单、流水、账户余额的一致性
   
5. **迁移方案**：生产环境建议迁移到RabbitMQ/Kafka，提供消息持久化和ACK机制
   - Spring Event适合单体应用的开发和学习场景
   - 生产环境推荐使用分布式消息队列保证可靠性
   - 迁移成本低：只需替换EventPublisher为RabbitTemplate/KafkaTemplate

---

#### 决策3：如何处理事件顺序性？

**方案**：
1. **事件链式设计**：每个事件触发下一个事件
2. **阶段标记**：订单状态标记当前处理阶段
3. **幂等性**：监听器支持重复消费

### 7.1 并发处理思路

#### 7.1.1 乐观锁机制

**应用场景**：
- 用户账户余额更新
- 商家账户余额更新
- 商品库存扣减

**实现方式**：
```sql
-- 扣减余额（乐观锁）
UPDATE user_account
SET balance = balance - #{amount},
    version = version + 1,
    updated_at = NOW()
WHERE user_id = #{userId}
  AND version = #{version}
  AND balance >= #{amount}
```

**重试机制**：
```java
int maxRetries = 3;
for (int retryCount = 0; retryCount < maxRetries; retryCount++) {
    try {
        // 执行业务逻辑
        int updatedRows = mapper.deductBalanceWithVersion(...);
        if (updatedRows == 0) {
            if (retryCount < maxRetries - 1) {
                // 指数退避重试
                long waitTime = (long) Math.pow(2, retryCount) * 100;
                Thread.sleep(waitTime);
                continue;
            } else {
                throw new OptimisticLockException("并发冲突，已重试" + maxRetries + "次");
            }
        }
        return; // 成功退出
    } catch (Exception e) {
        // 异常处理
    }
}
```

**实现步骤1：自定义限流注解**

```java
@Target({ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface RateLimit {
    String key() default "";                    // 限流key模板（支持SpEL）
    double permitsPerSecond();                  // QPS限制
    long timeout() default 1;                   // 获取令牌超时时间（秒）
    String message() default "系统繁忙，请稍后重试";
}
```

**实现步骤2：限流拦截器（核心组件）**

```java
@Component
@Slf4j
public class RateLimitInterceptor implements HandlerInterceptor {
    
    /**
     * 限流器缓存：key -> RateLimiter
     */
    private final ConcurrentHashMap<String, RateLimiter> limiterMap = new ConcurrentHashMap<>();
    
    /**
     * SpEL表达式解析器
     */
    private final ExpressionParser parser = new SpelExpressionParser();
    
    /**
     * 编译后的SpEL表达式缓存
     * key: 表达式字符串, value: 编译后的Expression对象
     * 在500 TPS高并发场景下，缓存可显著减少解析开销
     */
    private final ConcurrentHashMap<String, org.springframework.expression.Expression> expressionCache = 
        new ConcurrentHashMap<>();
    
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) 
            throws Exception {
        
        if (!(handler instanceof HandlerMethod)) {
            return true;
        }
        
        HandlerMethod handlerMethod = (HandlerMethod) handler;
        Method method = handlerMethod.getMethod();
        
        RateLimit rateLimit = method.getAnnotation(RateLimit.class);
        if (rateLimit == null) {
            return true;
        }
        
        // 构建限流key
        String limitKey = buildLimitKey(rateLimit.key(), request, handlerMethod);
        
        // 获取或创建限流器
        RateLimiter limiter = limiterMap.computeIfAbsent(limitKey, k -> 
            RateLimiter.create(rateLimit.permitsPerSecond())
        );
        
        // 尝试获取令牌
        if (!limiter.tryAcquire(rateLimit.timeout(), TimeUnit.SECONDS)) {
            log.warn("触发限流: key={}, uri={}, method={}", 
                limitKey, request.getRequestURI(), method.getName());
            
            writeRateLimitResponse(response, rateLimit.message());
            return false;
        }
        
        return true;
    }
    
    /**
     * 解析SpEL表达式（带缓存优化）
     */
    private String parseSpEL(String expression, HttpServletRequest request, 
                             HandlerMethod handlerMethod) {
        try {
            // 从缓存获取或编译表达式（线程安全）
            org.springframework.expression.Expression compiledExpression = 
                expressionCache.computeIfAbsent(expression, expr -> parser.parseExpression(expr));
            
            EvaluationContext context = new StandardEvaluationContext();
            context.setVariable("request", request);
            
            return compiledExpression.getValue(context, String.class);
        } catch (Exception e) {
            log.error("SpEL表达式解析失败: {}", expression, e);
            return "default:" + request.getRequestURI();
        }
    }
}
```

- ✅ **完全解耦**：限流逻辑与业务逻辑完全分离
- ✅ **统一入口**：所有限流在拦截器中统一处理
- ✅ **易于测试**：可以单独测试限流逻辑
- ✅ **便于监控**：可以在拦截器中统一收集限流指标
- ✅ **Spring原生支持**：无需额外依赖，稳定可靠
- ✅ **线程安全**：使用ConcurrentHashMap保证多线程环境下的安全性，limiterMap的computeIfAbsent方法是原子操作

---

### 7.2 事务与一致性策略

#### 7.2.1 事务策略

**同步事务（充值、添加库存）**：
- 使用`@Transactional`注解
- 事务范围最小化（仅包含必要的数据库操作）
- 事务持有锁时间 < 100ms（P95）

**事件驱动事务（下单）**：
- 每个阶段独立事务
- 通过事件串联，保证最终一致性
- 事务提交后立即发布事件（@TransactionalEventListener）

---

#### 7.2.2 一致性保证

**强一致性场景**：
- 用户充值：余额立即更新
- 添加库存：库存立即更新

**最终一致性场景**：
- 订单创建：通过事件链保证最终一致
- 补偿机制：失败时自动回滚

**对账机制**：
- T+1对账：每天凌晨02:00执行
- 对比销售总额和收款总额
- 不一致时告警，人工介入

### 7.3 缓存与性能优化方向

#### 7.3.1 当前方案（无缓存）

**原因**：
- 单体应用，数据量不大
- 避免缓存一致性问题
- 简化架构，降低复杂度

**性能保障**：

## 八、非功能设计

### 8.1 可用性设计

#### 8.1.1 容错机制

**事件重试**：
- 监听器内部重试3次（指数退避）
- 重试间隔：100ms, 200ms, 400ms
- 最后一次失败后发布OrderFailedEvent

**降级策略**：
- 数据库连接失败 → 返回友好错误提示
- 事件处理失败 → 记录异常表，人工介入
- 限流触发 → 返回429状态码 + Retry-After头

---

#### 8.1.2 故障恢复

**故障场景**：
- 应用重启：未处理事件可能丢失
- 数据库异常：事务自动回滚
- 网络抖动：重试机制处理

**恢复措施**：
- 事件持久化 + 定时重发
- T+1对账发现不一致
- 异常记录表人工处理
- 故障恢复时间 < 60秒（包含数据库连接池重建、Spring容器初始化、缓存预热等完整流程）

---

### 8.2 扩展性设计

#### 8.2.1 横向扩展思路

**当前架构**：
- 单体应用，垂直扩展为主
- 数据库读写分离（可选）

**未来扩展**：
- 微服务拆分：按限界上下文拆分
- 消息队列：Spring Event迁移到RabbitMQ/Kafka
- 分布式缓存：引入Redis集群
- 负载均衡：Nginx + 多实例部署

---

#### 8.2.2 模块化扩展

**新增功能**：

- 不影响现有模块
- 符合开闭原则

**示例**：

## 十二、总结与展望

### 12.1 架构亮点

1. ✅ **DDD领域驱动设计**：清晰划分限界上下文，聚合根保证数据一致性
2. ✅ **事件驱动架构**：模块解耦，异步处理，提升并发性能
3. ✅ **分层限流策略**：接口级+用户级双层保护，零代码侵入
4. ✅ **乐观锁重试机制**：高并发场景下保证数据一致性
5. ✅ **完善补偿机制**：失败自动回滚，T+1对账保证最终一致
6. ✅ **配置化管理**：限流规则、业务参数均可配置，易于调整
7. ✅ **可扩展性强**：新增业务只需添加监听器，符合开闭原则

---

### 12.2 待优化项

1. **事件持久化**：当前使用Spring Event，生产环境建议迁移到RabbitMQ/Kafka

3. **监控告警**：补充Prometheus + Grafana监控体系
4. **链路追踪**：引入SkyWalking或Zipkin追踪事件链路
