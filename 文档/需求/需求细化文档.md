，# 商品交易系统需求细化文档

## 一、文档说明

### 1.1 文档目的
本文档基于原始需求，结合领域驱动设计（DDD）方法论，对商品交易系统进行详细的需求分析和细化，明确业务边界、领域模型、业务流程和技术实现细节。

### 1.2 适用范围
- 系统架构设计
- 领域模型构建
- API接口设计
- 数据库设计
- 测试用例编写

### 1.3 术语定义

| 术语 | 定义 |
|-----|------|
| SKU | Stock Keeping Unit，库存量单位，商品的唯一标识 |
| 预存账户 | 用户预先充值的现金账户，用于购买商品支付 |
| 聚合根 | DDD中保证数据一致性的根实体，外部只能通过聚合根访问内部对象 |
| 限界上下文 | DDD中明确划分业务边界的上下文环境 |
| 领域事件 | 领域中发生的重要事情，用于解耦和异步通信 |
| 最终一致性 | 分布式系统中，数据经过一段时间后达到一致状态 |

## 二、业务场景分析

### 2.1 核心业务流程

#### 场景1：用户充值流程
```
用户发起充值请求 
  → 验证充值金额合法性 
  → 更新用户账户余额 
  → 记录充值流水 
  → 返回充值结果
```

**业务规则**：
- 充值金额必须大于0
- 支持最小充值单位：0.01元
- 单次充值上限：10,000元（可配置）
- 每日充值上限：50,000元（可配置）
- 充值请求需具备幂等性（防止重复充值）

#### 场景2：商家添加库存流程
```
商家发起添加库存请求 
  → 验证SKU合法性 
  → 验证商品价格 > 0 
  → 验证库存数量 > 0 
  → 判断SKU是否存在
    ├─ 存在：累加库存数量
    └─ 不存在：创建新商品库存记录
  → 返回操作结果
```

**业务规则**：
- SKU格式规范：大写字母+数字+下划线（如：IPHONE_15_PRO_256G）
- 商品价格精度：2位小数
- 单次添加库存上限：9,999件（可配置）
- 同一商家下SKU唯一
- 允许更新已存在商品的价格

#### 场景3：用户下单购买流程（核心流程）

```
【阶段1：订单创建 - 同步】
用户发起下单请求（SKU + 数量）
  → 验证用户身份
  → 查询商品信息（价格、库存）
  → 验证库存充足性
  → 计算订单总金额（quantity × price）
  → 验证用户余额充足性
  → 创建订单记录（状态=CREATED）
  → 发布"订单创建事件"到MQ
  → 返回订单ID给前端

【阶段2：资金扣减 - 异步】
用户服务消费"订单创建事件"
  → 获取分布式锁 lock:user:{userId}
  → 再次验证余额充足性（防止并发问题）
  → 扣减用户余额
  → 记录扣款流水
  → 发布"用户扣款成功事件"或"扣款失败事件"

【阶段3：库存扣减与收款 - 异步】
商家服务消费"订单创建事件"
  → 获取分布式锁 lock:inventory:{sku}
  → 验证库存充足性（防止超卖）
  → 扣减库存数量
  → 增加已售数量
  → 发布"库存扣减成功事件"或"扣减失败事件"
  
  → 获取分布式锁 lock:merchant:{merchantId}
  → 增加商家账户余额
  → 记录收款流水
  → 发布"商家收款成功事件"

【阶段4：订单状态更新 - 异步】
交易服务消费所有子事件
  → 等待所有事件到达（用户扣款、库存扣减、商家收款）
  → 判断结果：
    ├─ 全部成功：更新订单状态为 COMPLETED
    └─ 任一失败：更新订单状态为 FAILED，触发补偿流程

【阶段5：补偿流程（失败场景）】
如果用户扣款成功但库存扣减失败：
  → 触发用户退款
  → 获取分布式锁 lock:user:{userId}
  → 回滚用户余额
  → 发布"用户退款成功事件"
  → 更新订单状态为 FAILED
```

**业务规则**：
- 单次购买数量上限：99件（可配置）
- 订单创建后不可修改订单项
- 订单超时时间：30分钟未支付自动取消（可选功能）
- 必须保证最终一致性（通过MQ重试+补偿机制）
- 防超卖：库存扣减时必须使用分布式锁
- 防余额异常：余额操作时必须使用分布式锁

#### 场景4：商家每日结算对账流程

```
定时任务触发（每天凌晨2点）
  → 遍历所有商家
  → 对每个商家执行：
    ├─ 统计昨日已售商品总价值
    │   Σ(已售数量 × 单价)，按SKU汇总
    ├─ 查询昨日商家账户增加金额
    │   从收款流水中汇总
    ├─ 对比两个金额
    │   ├─ 一致：对账状态 = MATCHED
    │   └─ 不一致：对账状态 = MISMATCHED，记录差异金额
    ├─ 生成对账记录
    └─ 如果不一致，发送告警通知
  → 记录任务执行日志
```

**业务规则**：
- 对账日期：自然日（00:00:00 - 23:59:59）
- 对账容忍度：0.00元（必须完全一致）
- 告警方式：邮件/短信/钉钉（可配置）
- 对账失败不影响正常业务，但需人工介入
- 支持手动重新对账（管理后台功能）

## 三、领域模型设计（DDD）

### 3.1 限界上下文划分

根据DDD战略设计，将系统划分为三个限界上下文：

```
┌──────────────────────────────────────────────┐
│           商品交易系统                         │
├────────────┬─────────────┬───────────────────┤
│ 用户上下文  │  交易上下文  │   商家上下文       │
│ (User BC)  │(Trade BC)   │ (Merchant BC)     │
└────────────┴─────────────┴───────────────────┘
```

#### 3.1.1 用户上下文（User Context）

**职责边界**：
- 管理用户预存账户
- 处理账户充值
- 处理账户扣款
- 管理充值记录

**不包含的职责**：
- ❌ 订单管理（属于交易上下文）
- ❌ 商品管理（属于商家上下文）
- ❌ 库存管理（属于商家上下文）

#### 3.1.2 商家上下文（Merchant Context）

**职责边界**：
- 管理商家账户
- 管理商品库存（SKU维度）
- 处理库存添加
- 处理库存扣减
- 处理商家收款
- 执行每日结算对账

**不包含的职责**：
- ❌ 订单管理（属于交易上下文）
- ❌ 用户账户管理（属于用户上下文）

#### 3.1.3 交易上下文（Trade Context）

**职责边界**：
- 管理订单生命周期
- 协调交易流程（发布事件、监听事件）
- 订单状态流转
- 订单查询

**不包含的职责**：
- ❌ 直接操作账户余额（由用户/商家服务处理）
- ❌ 直接操作库存（由商家服务处理）

### 3.2 聚合根设计

#### 3.2.1 用户上下文聚合根

**聚合根：UserAccount（用户账户）**

```java
UserAccount (Aggregate Root)
├── UserId: Long（用户ID，主键）
├── Balance: Money（余额值对象）
│   ├── amount: BigDecimal（金额）
│   └── currency: String（货币类型，CNY）
├── Version: Integer（乐观锁版本号）
├── CreatedAt: LocalDateTime（创建时间）
└── UpdatedAt: LocalDateTime（更新时间）

方法：
├── recharge(amount: Money): void（充值）
├── deduct(amount: Money): void（扣款）
├── refund(amount: Money): void（退款）
└── getBalance(): Money（查询余额）

不变式约束：
├── Balance.amount >= 0（余额不能为负）
├── amount > 0（操作金额必须大于0）
└── currency == "CNY"（仅支持人民币）
```

**实体：RechargeRecord（充值记录）**

```java
RechargeRecord (Entity)
├── RechargeId: String（充值流水号，雪花算法）
├── UserId: Long（用户ID）
├── Amount: Money（充值金额）
├── Status: RechargeStatus（状态枚举）
│   ├── SUCCESS（成功）
│   └── FAILED（失败）
├── RequestId: String（请求ID，幂等性）
└── CreatedAt: LocalDateTime（创建时间）
```

**值对象：Money（金额）**

```java
Money (Value Object)
├── amount: BigDecimal（金额，精度2位小数）
└── currency: String（货币类型）

方法：
├── add(other: Money): Money（加法）
├── subtract(other: Money): Money（减法）
├── multiply(factor: int): Money（乘法）
└── isPositive(): boolean（是否大于0）

特性：
└── 不可变性（Immutable）
```

#### 3.2.2 商家上下文聚合根

**聚合根：MerchantAccount（商家账户）**

```java
MerchantAccount (Aggregate Root)
├── MerchantId: Long（商家ID，主键）
├── Balance: Money（当前余额）
├── TotalIncome: Money（累计收入）
├── Version: Integer（乐观锁版本号）
├── CreatedAt: LocalDateTime
└── UpdatedAt: LocalDateTime

方法：
├── credit(amount: Money): void（收款）
├── getBalance(): Money（查询余额）
└── getTotalIncome(): Money（查询累计收入）

不变式约束：
├── Balance.amount >= 0
└── amount > 0
```

**聚合根：ProductInventory（商品库存）**

```java
ProductInventory (Aggregate Root)
├── Id: Long（主键）
├── MerchantId: Long（商家ID）
├── Sku: String（商品SKU，唯一标识）
├── ProductName: String（商品名称）
├── Price: Money（单价）
├── StockQuantity: int（库存数量）
├── SoldQuantity: int（已售数量）
├── LockedQuantity: int（锁定数量，预留扩展）
├── Version: Integer（乐观锁版本号）
├── CreatedAt: LocalDateTime
└── UpdatedAt: LocalDateTime

方法：
├── addStock(quantity: int): void（添加库存）
├── deductStock(quantity: int): void（扣减库存）
├── updatePrice(newPrice: Money): void（更新价格）
├── getAvailableStock(): int（获取可用库存）
└── isStockSufficient(quantity: int): boolean（库存是否充足）

不变式约束：
├── StockQuantity >= 0（库存不能为负）
├── SoldQuantity >= 0
├── Price.amount > 0（价格必须大于0）
├── quantity > 0（操作数量必须大于0）
└── StockQuantity >= quantity（扣减时库存充足）

计算字段：
└── AvailableStock = StockQuantity - LockedQuantity
```

**实体：SettlementRecord（结算记录）**

```java
SettlementRecord (Entity)
├── SettlementId: String（结算ID）
├── MerchantId: Long（商家ID）
├── SettlementDate: LocalDate（结算日期）
├── TotalSalesAmount: Money（销售总额）
├── AccountIncreaseAmount: Money（账户增加额）
├── DiscrepancyAmount: Money（差异金额）
├── Status: SettlementStatus（状态）
│   ├── MATCHED（一致）
│   └── MISMATCHED（不一致）
└── CreatedAt: LocalDateTime

方法：
└── isMatched(): boolean（是否对账一致）
```

#### 3.2.3 交易上下文聚合根

**聚合根：Order（订单）**

```java
Order (Aggregate Root)
├── OrderId: String（订单ID，雪花算法）
├── UserId: Long（用户ID）
├── MerchantId: Long（商家ID）
├── Status: OrderStatus（订单状态）
│   ├── CREATED（已创建）
│   ├── PAYING（支付中）
│   ├── PAID（已支付）
│   ├── COMPLETED（已完成）
│   ├── CANCELLED（已取消）
│   └── FAILED（失败）
├── OrderItems: List<OrderItem>（订单项列表）
├── TotalAmount: Money（订单总金额）
├── CreateTime: LocalDateTime（创建时间）
├── PayTime: LocalDateTime（支付时间，可为空）
├── Version: Integer（乐观锁版本号）
└── DomainEvents: List<DomainEvent>（领域事件列表）

方法：
├── addItem(item: OrderItem): void（添加订单项）
├── calculateTotalAmount(): Money（计算总金额）
├── markAsPaying(): void（标记为支付中）
├── markAsCompleted(): void（标记为已完成）
├── markAsFailed(): void（标记为失败）
├── cancel(): void（取消订单）
└── getStatus(): OrderStatus（获取状态）

不变式约束：
├── OrderItems 不为空
├── TotalAmount = Σ(OrderItem.subtotal)
├── 订单创建后不可修改 OrderItems
├── 状态只能单向流转（除CANCELLED外）
└── PayTime 仅在状态变为 COMPLETED 时设置

领域事件：
├── OrderCreatedEvent（订单创建事件）
├── OrderCompletedEvent（订单完成事件）
└── OrderFailedEvent（订单失败事件）
```

**值对象：OrderItem（订单项）**

```java
OrderItem (Value Object)
├── ItemId: Long（项ID）
├── Sku: String（商品SKU）
├── ProductName: String（商品名称）
├── Quantity: int（购买数量）
├── UnitPrice: Money（单价）
└── Subtotal: Money（小计）

方法：
└── calculateSubtotal(): Money（计算小计）

不变式约束：
├── Quantity > 0
├── UnitPrice.amount > 0
└── Subtotal = Quantity × UnitPrice

特性：
└── 不可变性（Immutable）
```

## 四、业务流程详细说明

### 4.1 用户充值流程

#### 4.1.1 流程图
```
┌──────────┐     ┌──────────────┐     ┌──────────────┐
│  客户端   │     │ user-service │     │   MySQL      │
└────┬─────┘     └──────┬───────┘     └──────┬───────┘
     │                  │                     │
     │ POST /recharge   │                     │
     │─────────────────>│                     │
     │                  │                     │
     │                  │ 1.验证金额合法性     │
     │                  │ 2.检查幂等性         │
     │                  │                     │
     │                  │ 3.开启事务           │
     │                  │────────────────────>│
     │                  │                     │
     │                  │ 4.更新账户余额       │
     │                  │ UPDATE user_account  │
     │                  │ SET balance = balance + ?
     │                  │ WHERE user_id = ?    │
     │                  │                     │
     │                  │ 5.插入充值记录       │
     │                  │ INSERT INTO recharge_record
     │                  │                     │
     │                  │ 6.提交事务           │
     │                  │────────────────────>│
     │                  │                     │
     │                  │ 7.标记幂等性         │
     │                  │                     │
     │  返回结果         │                     │
     │<─────────────────│                     │
     │                  │                     │
```

#### 4.1.2 业务规则细化

**前置条件**：
- 用户ID必须存在
- 充值金额范围：0.01 ~ 10,000元
- 请求ID必须唯一（UUID或雪花算法）

**后置条件**：
- 用户账户余额增加相应金额
- 充值记录状态为SUCCESS
- 返回最新余额

**异常处理**：
- 金额不合法 → 返回400错误
- 重复请求ID → 返回成功（幂等性）
- 数据库异常 → 返回500错误，记录日志

#### 4.1.3 测试场景

| 场景编号 | 测试场景 | 输入 | 预期输出 |
|---------|---------|------|---------|
| TC-001 | 正常充值 | userId=1001, amount=100.00 | 余额增加100，返回成功 |
| TC-002 | 充值金额为0 | amount=0 | 返回400错误 |
| TC-003 | 充值金额为负数 | amount=-50 | 返回400错误 |
| TC-004 | 充值金额超限 | amount=20000 | 返回400错误 |
| TC-005 | 重复请求ID | requestId相同 | 返回成功（幂等） |
| TC-006 | 并发充值 | 同时发起2次充值 | 两次都成功，余额正确累加 |

#### 4.2.2 业务规则细化

**前置条件**：
- 商家ID必须存在
- SKU格式：`^[A-Z0-9_]+$`（大写字母、数字、下划线）
- 商品名称长度：1~255字符
- 价格范围：0.01 ~ 999,999.99元
- 数量范围：1 ~ 9,999件

**后置条件**：
- 如果SKU存在：库存数量累加，可选更新价格
- 如果SKU不存在：创建新库存记录
- 返回最新库存数量

**异常处理**：
- SKU格式错误 → 返回400错误
- 价格不合法 → 返回400错误
- 数量不合法 → 返回400错误
- 数据库异常 → 返回500错误

#### 4.3.2 业务规则细化

**前置条件**：
- 用户ID和商家ID必须存在
- SKU必须在商家库存中存在
- 库存数量 >= 请求购买数量
- 用户余额 >= 订单总金额（quantity × price）
- 购买数量范围：1 ~ 99

**订单创建阶段规则**：
- 订单ID使用雪花算法生成，全局唯一
- 订单初始状态：CREATED
- 订单项创建后不可修改
- 订单总金额 = Σ(订单项小计)
- 必须记录创建时间

**扣款阶段规则**：
- 必须获取分布式锁 `lock:user:{userId}`
- 扣款前再次验证余额（防止并发）
- 扣款后余额不能为负
- 必须记录扣款流水
- 操作必须具备幂等性

**库存扣减阶段规则**：
- 必须获取分布式锁 `lock:inventory:{sku}`
- 扣减前再次验证库存（防止超卖）
- 库存扣减后不能为负
- 已售数量相应增加
- 操作必须具备幂等性

**收款阶段规则**：
- 必须获取分布式锁 `lock:merchant:{merchantId}`
- 收款金额 = 订单总金额
- 累计收入相应增加
- 必须记录收款流水
- 操作必须具备幂等性

**订单状态更新规则**：
- 所有子步骤成功 → 状态变更为 COMPLETED
- 任一子步骤失败 → 状态变更为 FAILED
- 状态变更必须记录时间戳
- 状态只能单向流转（CREATED → COMPLETED/FAILED）

**补偿流程规则**：
- 用户扣款成功 + 库存扣减失败 → 触发用户退款
- 用户退款必须获取分布式锁
- 退款后余额恢复
- 记录退款流水
- 最终订单状态为 FAILED

#### 4.3.3 异常场景处理

**场景1：用户余额不足**
```
发生时机：用户服务消费订单事件时
处理方式：
  1. 发布 UserDeductFailedEvent
  2. 交易服务接收事件
  3. 更新订单状态为 FAILED
  4. 无需补偿（用户未扣款）
  5. 返回错误信息给前端
```

**场景2：库存不足（并发导致）**
```
发生时机：商家服务消费订单事件时
处理方式：
  1. 发布 InventoryDeductFailedEvent
  2. 交易服务接收事件
  3. 更新订单状态为 FAILED
  4. 发布补偿事件触发用户退款
  5. 用户服务执行退款
  6. 返回错误信息给前端
```

**场景3：MQ消息丢失**
```
预防措施：
  1. 生产者开启确认机制（publisher-confirm）
  2. 消息持久化到磁盘
  3. 消费者手动ACK
  
补救措施：
  1. 定时任务扫描超时订单（>5分钟仍为CREATED）
  2. 重新发布订单事件
  3. 消费者检查幂等性，避免重复处理
```

**场景4：消费者处理失败**
```
处理方式：
  1. MQ自动重试（最多3次）
  2. 重试间隔：1s, 2s, 4s（指数退避）
  3. 重试仍失败 → 进入死信队列
  4. 告警通知人工介入
  5. 支持手动重新投递消息
```

**场景5：分布式锁获取失败**
```
处理方式：
  1. 等待5秒后重试
  2. 重试3次仍失败 → 抛出异常
  3. 订单状态保持 CREATED
  4. 定时任务后续处理
```

#### 4.4.2 业务规则细化

**执行时间**：
- 默认：每天凌晨02:00
- 可配置：通过配置文件调整cron表达式
- 时区：服务器本地时区

**对账范围**：
- 日期范围：昨日 00:00:00 ~ 23:59:59
- 商家范围：所有活跃商家
- 数据类型：已完成订单（status=COMPLETED）

**销售总额计算**：
```sql
SELECT 
    merchant_id,
    SUM(order_item.quantity * order_item.unit_price) AS total_sales
FROM order_item
JOIN orders ON order_item.order_id = orders.order_id
WHERE orders.merchant_id = ?
  AND orders.status = 'COMPLETED'
  AND DATE(orders.pay_time) = ?
GROUP BY merchant_id
```

**收款总额计算**：
```sql
SELECT 
    merchant_id,
    SUM(amount) AS total_received
FROM merchant_credit_record
WHERE merchant_id = ?
  AND DATE(created_at) = ?
GROUP BY merchant_id
```

**对账判断**：
- 一致：`total_sales == total_received`
- 不一致：`total_sales != total_received`
- 差异金额：`discrepancy = total_sales - total_received`

**告警规则**：
- 对账不一致时立即告警
- 告警内容：商家ID、日期、销售总额、收款总额、差异金额
- 告警渠道：邮件 + 钉钉（可配置）
- 告警级别：P1（高优先级）

**重试机制**：
- 对账失败（异常）不中断其他商家对账
- 记录失败日志
- 支持手动重新对账

### 7.1 性能要求

| 指标 | 目标值 | 说明 |
|-----|--------|------|
| 系统可用性 | > 99.9% | 年度可用性 |

| 故障恢复时间 | < 5分钟 | 服务故障后恢复时间 |

### 7.3 安全性要求

1. **数据安全**：
   - 敏感数据加密存储（如用户信息）
   - SQL注入防护
   - XSS攻击防护

2. **接口安全**：
   - API鉴权（JWT Token）

## 十、风险与应对

### 10.1 技术风险

| 风险 | 影响 | 应对措施 |
|-----|------|---------|
| MQ消息丢失 | 数据不一致 | 消息持久化 + 生产者确认 + 定时对账 |
| 分布式锁失效 | 并发安全问题 | Redis集群 + 看门狗机制 |
| 数据库死锁 | 服务不可用 | 优化SQL + 超时检测 + 自动重试 |
| 内存泄漏 | 服务崩溃 | JVM监控 + GC日志分析 |

### 10.2 业务风险

| 风险 | 影响 | 应对措施 |
|-----|------|---------|
| 超卖 | 商家损失 | 分布式锁 + 库存预扣减 |
| 重复扣款 | 用户投诉 | 幂等性设计 + 分布式锁 |
| 对账不一致 | 财务风险 | 每日对账 + 告警机制 |
| 恶意刷单 | 系统压力 | 频率限制 + 风控规则 |
