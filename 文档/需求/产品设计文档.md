# 商品交易系统产品设计文档

## 一、产品概述

### 1.1 产品背景

随着电商行业的快速发展，构建一个稳定、可靠的商品交易系统成为核心需求。本系统旨在实现用户与商家之间的商品交易流程，包括用户充值、商品库存管理、下单购买、资金结算等核心功能。

本产品定位为**技术演示项目**，主要用于展示系统设计能力和编码水平，适用于技术面试场景。因此，产品设计需要在保证功能完整性的同时，注重代码质量、可扩展性和可维护性。

### 1.2 产品目标

#### 业务目标
- 实现完整的商品交易闭环：充值 → 上架 → 下单 → 支付 → 结算
- 保证交易的准确性和一致性，避免超卖、重复扣款等问题
- 提供清晰的账务对账机制，确保财务数据准确

#### 技术目标
- 采用DDD领域驱动设计，合理划分业务边界
- 实现高内聚低耦合的模块化设计
- 核心代码单元测试覆盖率达到80%以上
- 具备良好的可扩展性，支持后续功能迭代

### 1.3 目标用户

| 用户角色 | 描述 | 核心需求 |
|---------|------|---------|
| 普通用户 | 购买商品的用户 | 账户充值、浏览商品、下单购买、查看订单 |
| 商家 | 提供商品的商家 | 商品上架、库存管理、查看收益、对账结算 |
| 系统管理员 | 系统运维人员 | 系统监控、异常处理、数据查询 |

### 1.4 使用场景

**场景1：新用户首次购物**
1. 用户注册并登录系统
2. 向预存账户充值100元
3. 浏览商品列表，选择心仪商品
4. 提交订单并完成购买
5. 查看订单状态和余额变化

**场景2：商家日常运营**
1. 商家登录系统
2. 添加新商品到库存（SKU、价格、数量）
3. 查看商品销售情况
4. 每日查看结算对账结果

**场景3：高并发抢购**
1. 多个用户同时购买同一热门商品
2. 系统保证只有库存足够的用户能成功购买
3. 避免超卖和数据不一致

### 2.2 核心功能详细说明

#### 2.2.1 用户账户充值

**功能描述**：用户可以通过REST API向自己的预存账户充值，支持人民币一种货币。

**用户故事**：
> 作为一个用户，我希望能够向我的预存账户充值，以便后续购买商品时使用。

**业务流程**：
```
用户发起充值请求 
  → 系统验证充值金额合法性（0.01 ~ 10,000元）
  → 系统检查幂等性（防止重复充值）
  → 系统更新用户账户余额
  → 系统记录充值流水
  → 返回充值结果和最新余额
```

**功能规则**：
- 充值金额范围：0.01元 ~ 10,000元（可配置）
- 最小充值单位：0.01元
- 单次充值上限：10,000元（可配置）
- 每日充值上限：50,000元（可配置）
- 必须支持幂等性：相同的requestId多次请求只处理一次
- 充值成功后立即更新余额，保证强一致性

**异常处理**：
- 充值金额为0或负数 → 返回400错误："充值金额必须大于0"
- 充值金额超过上限 → 返回400错误："充值金额超出限制"
- 用户不存在 → 返回404错误："用户不存在"
- 系统异常 → 返回500错误，记录日志

**验收标准**：
- ✅ 正常充值后，余额正确增加
- ✅ 重复requestId不会重复充值
- ✅ 并发充值时，余额正确累加
- ✅ 异常情况有明确的错误提示

---

#### 2.2.2 商家商品库存管理

**功能描述**：商家可以通过REST API向库存中添加商品，包括设置SKU、价格、数量等信息。

**用户故事**：
> 作为一个商家，我希望能够添加商品到库存中，设置价格和数量，以便用户可以购买。

**业务流程**：
```
商家发起添加库存请求 
  → 系统验证SKU格式（大写字母+数字+下划线）
  → 系统验证价格 > 0
  → 系统验证数量 > 0
  → 判断SKU是否存在
    ├─ 存在：累加库存数量，可选更新价格
    └─ 不存在：创建新商品库存记录
  → 返回操作结果和最新库存信息
```

**功能规则**：
- SKU格式规范：`^[A-Z0-9_]+$`（如：IPHONE_15_PRO_256G）
- 商品价格精度：2位小数，范围0.01 ~ 999,999.99元
- 单次添加库存上限：9,999件（可配置）
- 同一商家下SKU唯一
- 如果SKU已存在，累加库存数量
- 允许更新已存在商品的价格

**异常处理**：
- SKU格式错误 → 返回400错误："SKU格式不正确"
- 价格为0或负数 → 返回400错误："商品价格必须大于0"
- 数量为0或负数 → 返回400错误："库存数量必须大于0"
- 数量超过上限 → 返回400错误："库存数量超出限制"

**验收标准**：
- ✅ 新增SKU成功创建库存记录
- ✅ 已有SKU累加库存数量
- ✅ 非法参数有明确的错误提示
- ✅ 并发添加库存时，数量正确累加

#### 2.2.3 用户下单购买（核心功能）

**功能描述**：用户提供SKU和购买数量，系统完成扣款、减库存、加商家余额的原子操作。

**用户故事**：
> 作为一个用户，我希望能够选择商品并提交订单，系统自动从我的账户扣款，减少库存，并将款项转入商家账户。

**业务流程**：
```
【方案A：同步事务（推荐 - 适合面试项目）】

用户发起下单请求（SKU + 数量）
  → 系统开启数据库事务
  → 验证用户身份
  → 查询商品信息（价格、库存）
  → 验证库存充足性
  → 计算订单总金额（quantity × price）
  → 验证用户余额充足性
  → 创建订单记录（状态=CREATED）
  → 扣减用户余额
  → 记录用户扣款流水
  → 扣减库存数量
  → 增加已售数量
  → 增加商家账户余额
  → 记录商家收款流水
  → 更新订单状态为 COMPLETED
  → 提交事务
  → 返回订单ID和结果给前端

【异常处理】
如果任一步骤失败：
  → 回滚整个事务
  → 返回错误信息
```

**功能规则**：
- 单次购买数量上限：99件（可配置）
- 订单创建后不可修改订单项
- 所有操作在一个数据库事务中完成，保证ACID
- 防超卖：使用乐观锁（version字段）或数据库行锁
- 防余额异常：使用乐观锁或数据库行锁
- 订单状态流转：CREATED → COMPLETED（成功）或 FAILED（失败）

**并发控制方案**：

**方案1：乐观锁（推荐）**
- 在user_account、product_inventory、merchant_account表中添加version字段
- 更新时检查版本号：`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?`
- 如果更新受影响行数为0，说明被其他事务修改，抛出异常

**方案2：数据库行锁**
- 查询时使用 `SELECT ... FOR UPDATE` 锁定行
- 适合高并发场景，但可能影响性能

**异常场景处理**：

| 异常场景 | 处理方式 |
|---------|---------|
| 用户余额不足 | 抛出InsufficientBalanceException，事务回滚，返回"余额不足" |
| 库存不足 | 抛出InsufficientStockException，事务回滚，返回"库存不足" |
| 数据库死锁 | 捕获DeadlockLoserDataAccessException，自动重试（最多3次） |
| 并发下单（同一商品） | 使用乐观锁，只有一个用户成功，其余提示"库存变化，请重新下单" |

**验收标准**：
- ✅ 正常下单后，用户余额、库存、商家余额正确更新
- ✅ 余额不足时，订单创建失败，无脏数据
- ✅ 库存不足时，订单创建失败，无脏数据
- ✅ 并发下单时，不会超卖
- ✅ 事务回滚时，所有数据恢复到初始状态

#### 2.2.4 商家每日结算对账

**功能描述**：系统每天凌晨2点自动执行对账任务，对比昨日销售总额和商家账户增加额，确保账务一致。

**用户故事**：
> 作为一个商家，我希望系统每天自动对账，确保我的销售数据和账户余额一致，如有差异能及时收到告警。

**业务流程**：
```
定时任务触发（每天凌晨02:00）
  → 遍历所有商家
  → 对每个商家执行：
    ├─ 统计昨日销售总额：Σ(已售数量 × 单价)，按SKU汇总
    ├─ 查询昨日商家账户增加金额：从收款流水中汇总
    ├─ 对比两个金额
    │   ├─ 一致：对账状态 = MATCHED
    │   └─ 不一致：对账状态 = MISMATCHED，记录差异金额
    ├─ 生成对账记录
    └─ 如果不一致，发送告警通知
  → 记录任务执行日志
```

**功能规则**：
- 对账日期：自然日（00:00:00 - 23:59:59）
- 对账容忍度：0.00元（必须完全一致）
- 告警方式：日志记录（可扩展为邮件/短信/钉钉）
- 对账失败不影响正常业务，但需人工介入
- 支持手动重新对账

**销售总额计算SQL**：
```sql
SELECT 
    merchant_id,
    SUM(order_item.quantity * order_item.unit_price) AS total_sales
FROM order_item
JOIN orders ON order_item.order_id = orders.order_id
WHERE orders.merchant_id = ?
  AND orders.status = 'COMPLETED'
  AND DATE(orders.create_time) = ?
GROUP BY merchant_id
```

**收款总额计算SQL**：
```sql
SELECT 
    merchant_id,
    SUM(amount) AS total_received
FROM merchant_credit_record
WHERE merchant_id = ?
  AND DATE(created_at) = ?
GROUP BY merchant_id
```

**验收标准**：
- ✅ 正常对账时，销售额和收款额一致，状态为MATCHED
- ✅ 数据不一致时，状态为MISMATCHED，记录差异金额
- ✅ 无交易数据时，销售额和收款额都为0，状态为MATCHED
- ✅ 对账任务异常时，记录错误日志，继续处理下一个商家

## 三、产品交互设计

### 3.1 API设计规范

#### 3.1.1 RESTful API 设计原则

1. **资源命名**：使用名词复数形式
2. **HTTP方法**：GET（查询）、POST（创建）、PUT（更新）、DELETE（删除）
3. **版本控制**：URL中包含版本号 `/api/v1/...`
4. **统一响应格式**：所有接口返回统一的JSON结构
5. **状态码规范**：正确使用HTTP状态码

#### 3.1.2 统一响应格式

**成功响应**：
```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": "2026-05-02T10:30:00"
}
```

**错误响应**：
```json
{
  "code": 400,
  "message": "充值金额不能为0",
  "data": null,
  "timestamp": "2026-05-02T10:30:00"
}
```

#### 3.1.3 HTTP状态码规范

| 状态码 | 说明 | 使用场景 |
|-------|------|---------|
| 200 | 成功 | 请求成功处理 |
| 400 | 请求错误 | 参数校验失败 |
| 404 | 资源不存在 | 用户/商品/订单不存在 |
| 500 | 服务器错误 | 系统内部异常 |

## 四、数据字典

### 4.1 枚举类型定义

#### OrderStatus（订单状态）
| 值 | 说明 | 描述 |
|----|------|------|
| CREATED | 已创建 | 订单已创建 |
| COMPLETED | 已完成 | 订单完成 |
| FAILED | 失败 | 订单处理失败 |

**说明**：简化订单状态，因为采用同步事务，订单创建后立即完成或失败，不需要中间状态。

#### RechargeStatus（充值状态）
| 值 | 说明 |
|----|------|
| SUCCESS | 成功 |
| FAILED | 失败 |

#### SettlementStatus（对账状态）
| 值 | 说明 |
|----|------|
| MATCHED | 一致 |
| MISMATCHED | 不一致 |

## 六、产品风险与应对

### 6.1 业务风险

| 风险 | 影响 | 可能性 | 应对措施 |
|-----|------|--------|---------|
| 超卖 | 商家损失，用户投诉 | 中 | 使用乐观锁或行锁保证原子性 |
| 重复扣款 | 用户投诉，财务损失 | 低 | 数据库事务保证原子性 |
| 对账不一致 | 财务风险 | 低 | 每日对账 + 告警机制 |
| 恶意刷单 | 系统压力 | 低 | 频率限制（可选） |

### 6.2 技术风险

| 风险 | 影响 | 可能性 | 应对措施 |
|-----|------|--------|---------|
| 数据库死锁 | 服务不可用 | 中 | 统一资源访问顺序 + 超时检测 + 自动重试 |
| 并发冲突 | 用户体验差 | 中 | 乐观锁 + 友好提示 |
| 事务长时间持有锁 | 性能下降 | 低 | 优化SQL，减少事务范围 |
